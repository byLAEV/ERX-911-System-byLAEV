## 3. Execution controls

1. Inspect the exact accepted source/version before extracting a source requirement.
2. Preserve the source's wording, scope, modality and locator.
3. Distinguish EXTRACTED, DERIVED and PROPOSED records.
4. Do not elevate examples, explanatory statements, recommendations or future plans to mandatory requirements without source support and explicit rationale.
5. Record unresolved ambiguity, contradiction, source gaps and unassigned verification criteria without silent reconciliation.
6. Keep requirements identification separate from requirement approval, technical implementation and institutional adoption.
7. Preserve the five accepted original PDFs; use their established WP-0.2 integrity evidence and current exact content for source locators.
8. Use the approved WP-0.3 hierarchy/subject-matter authority and WP-0.4 document control policy; do not create new precedence rules.

## 4. Initial execution state

The existing ERX-REQUIREMENTS-METHOD-001 v0.1.0 is a preparatory draft, not an approved method. The requirements traceability CSV is a schema-only baseline. These are inputs to WP-0.7 execution, not evidence that requirements have already been extracted.

The first execution sequence is:
- finalize and control the extraction method;
- record direct source-inspection evidence and source locators;
- begin requirement extraction with exact citations and status separation;
- synchronize the traceability register and supporting decision/open-issue records.

## 5. Boundaries

WP-0.7 does not authorize protocol amendment, operational consensus approval, implementation, deployment, institutional operation, Phase 1 or external homologation. Requirements that need decisions remain pending and must be routed through the approved governance/decision process.
